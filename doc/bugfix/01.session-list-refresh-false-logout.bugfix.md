## 1. 变更提案（Bug 背景）

> 对应传统文档：PRD / 缺陷报告 | 职责：业务背景、缺陷现象、修复目标、验收标准

### 1.1 背景与动机

扩展 popup 已重构为「会话管理器」（v1.0.12）：打开即自动 `LOAD_SESSIONS` 拉全量列表，支持勾选批量导出与学习式批量删除。列表来源是 DeepSeek 页面的 `chat_session/fetch_page` 内部 API。

**缺陷现象**（用户报告，v1.0.13，Chrome 扩展）：

- 点击「刷新列表」失败，popup 顶部红条：`加载会话列表失败: Error: Error: 未登录或登录已过期，请先登录 chat.deepseek.com 后重试`

- popup「API 捕获诊断」只列出 5 条 `/api/` 请求，**其中没有任何 `fetch_page`**：
  `/api/v0/telemetry`、`/api/v0/client/settings/report`、`/api/v0/chat/create_pow_challenge`、`/api/v0/chat_session/create`、`/api/v0/users/auth_token/check_device`

**运行日志关键三行**（`2026-10-30T02:19:10`）：


### 1.4 风险评估

- **主路径零改动**：`fetchPageRequest` 存在时仍原样重放（`method/url/body` 一致），只有捕获缺失才走新兜底，行为与旧版「捕获成功」时等价。
- **可回退**：改动集中在 2 个文件的兜底分支 + 1 个新工具函数，无数据迁移、无接口契约变更。
- **翻页语义更贴页面**：新增 `lte_cursor.pinned` 与页面自身 `touchCursor` 行为对齐；即便服务端忽略该参数，也只是退化为按 `updated_at` 翻页（与修复前一致）。
- **业务错误码判定偏保守**：仅当响应同时具备 `code≠0`、非空 `msg`、存在 `data` 字段时判定为错误包络，避免把业务对象里的 `code` 字段误当错误码。
- **遗留风险（本次未消除）**：hook 仍是「异步注入」，理论上存在「页面请求早于 hook 安装」的竞态，见 §5.4。

## 2. 技术方案

> 对应传统文档：Design Doc / Architecture | 职责：根因分析、修复方案、数据流、文件变更

### 2.1 根因分析：为什么"未登录"

#### 2.1.1 调用链

```
popup loadList()
  → SW 'LOAD_SESSIONS' → loadAllSessions()
      → content 'EXPORT_ALL' 取模板 { fetchPageRequest, historyRequest }
      → fetchAllSessions(tabId, fetchPageRequest)
          → 每页 proxyRequest() → content 'FETCH_PROXY' → proxyFetch() 在页面上下文带 Bearer Token 请求
          → extractSessions() 容错解析 → keyset 游标翻页
```

`fetchAllSessions` 在模板缺失时会退到硬编码请求（`service-worker.ts:311-318`）：

```ts
let req: CapturedApiRequest = fetchPageRequest || {
  kind: 'fetchPage',
  url: `${API_BASE}/api/chat_session/fetch_page`,   // ← 缺 /v0/
  method: 'POST',
  body: JSON.stringify({ cursor: '', limit: SESSION_PAGE_SIZE, order_by: 'updated_at', direction: 'DESC' }),
};
```

#### 2.1.2 缺陷代码（修复前，HEAD `a3aa752`）

`content/index.ts:347-359` 把「非 JSON 响应」兜成未登录：

```ts
if (!contentType.includes('application/json')) {
  const text = await response.text();
  logger.error('Proxy fetch 返回非 JSON 响应', { url: payload.url, contentType, bodySnippet: text.slice(0, 500) });
  // API 返回 HTML：结合 token 缺失或页面特征判断为未登录（被重定向到登录页）
  if (!authToken || /<html|login/i.test(text.slice(0, 1000))) {
    throw new Error('未登录或登录已过期，请先登录 chat.deepseek.com 后重试');
  }
  throw new Error(`响应非 JSON（content-type: ${contentType}），URL 可能不正确`);
}
```

**两个叠加缺陷**：

1. **路径缺版本段**：`/api/chat_session/fetch_page` 在后端不存在，被 SPA 的 history fallback 接住 → **HTTP 200 + `index.html`**，不是 401/403，所以 `response.ok` 为真，问题被推迟到 content-type 判断。
2. **HTML ⇒ 未登录的错误归因**：`/<html|login/i` 会命中任意 SPA 文档（`<!doctype html>...<title>DeepSeek</title>`，且描述文案含 "login" 之类词），于是「URL 错了」被写成「你没登录」。

#### 2.1.3 线上实测证据（2026-10-30，未登录 curl）

| 请求 | HTTP | `content-type` | body |
|------|------|----------------|------|
| `GET /api/v0/chat_session/fetch_page` | 200 | `application/json` | `{"code":40003,"msg":"INVALID_TOKEN","data":null}` |
| `GET /api/chat_session/fetch_page` | 200 | `text/html; charset=utf-8` | `<html lang="en">...<title>DeepSeek</title>...` |
| `POST /api/v0/chat_session/fetch_page` | 200 | `application/json` | 同 `INVALID_TOKEN`（鉴权先于 method 校验，故 POST 不构成独立证据） |

返回的 HTML 中 `meta[name=commit-id]` 为 `26090614`，**与用户日志里的 bodySnippet 完全一致**，可确认命中的就是同一份 SPA 文档。

#### 2.1.4 页面侧真实调用（逆向 `main.d1d163b7e4.js`，commit-id `26090614`）

```js
o.http.get("/api/v0/chat_session/fetch_page", {
  query: "gte" === n
    ? { "gte_cursor.pinned": s, "gte_cursor.updated_at": r, count: t }
    : { "lte_cursor.pinned": s, "lte_cursor.updated_at": r, count: t },
})
```

游标对象由 `{pinned, value}` 经 `spread` 得到：`{ pinned: e.pinned || false, updatedAt: e.value }`；初始 store 为 `cursor: { pinned: null, value: null }`，因此**首页请求里 `updated_at` 为 null、被序列化时省略**。

列表加载触发点（非置顶分组组件）：

```js
c = rV().fetchSessions;
(0, eE.useLayoutEffect)(() => { c() }, [c]);   // 组件挂载即请求首页
```

> 结论：页面**每次挂载侧栏列表都会主动请求 `fetch_page`**，不存在"命中本地缓存所以不发请求"（`localStorage` 里只有 `__session_page_size__`）。这推翻了排障初期的第 1 个假设。

#### 2.1.5 为什么"以前是好的"——版本溯源

| 版本 | 提交 | 与本次故障的关系 |
|------|------|------------------|
| v1.0.0 | `adebc0f` | 兜底写死 `POST /api/chat_session/fetch_page`，**这条路径从来不存在**（潜在缺陷起点） |
| v1.0.6 | `a2617b6` | 提交信息自述"修复代理请求返回 HTML（`<!doctype...is not valid JSON`）"，做法是 `findCapturedUrl('chat_session/fetch_page')` 扫 `recentApiUrls` 取真实端点 —— **绕开而非修好兜底** |
| v1.0.7 | `b9134f1` | 为修批量导出 405 改为「重放捕获的 method/url/body」，url 发现机制退场 |

> **被推翻的假设 2**：曾怀疑「v1.0.7 移除 url 自愈」是主因。核对后不成立——自愈依赖 `recentApiUrls`、重放依赖 `capturedRequests`，二者在"页面一条 `fetch_page` 都没发"时**同时为空**，v1.0.6 也救不回来。故 v1.0.7 不是本案凶手。

### 2.2 修复方案（ADR）

#### ADR-1：兜底请求按 v0 协议构造，而不是"再猜一个 URL"

- **决策**：兜底固定为 `GET /api/v0/chat_session/fetch_page?lte_cursor.pinned=false&count=<页大小>`，`count` 缺省交给服务端默认值；首页**不传** `lte_cursor.updated_at`（页面初始游标为 null）。
- **理由**：`method` / `path` / 参数形态全部取自页面自身 bundle，不凭约定猜测；与 v1.0.6 的教训一致——猜 URL 的代价是一次误导性故障。
- **被否决的替代**：① 继续 POST + JSON body（无证据支持，且非页面行为）；② 只在 SW 里硬编码 `/v0/`（接口再变就再坏一次）。

#### ADR-2：端点自愈放在 content 侧，基于已捕获 URL

- **决策**：`findRequest('fetchPage')` 在 `capturedRequests` 为空时，扫描 `recentApiUrls` 找 `includes('chat_session/fetch_page')`，命中则用 `buildFetchPageFallback` 剔除游标参数、保留 `count` 后返回 GET 模板。
- **理由**：`recentApiUrls` 对**所有** `/api/` 请求都记录（`noteApiUrl`），比 `CapturedApiRequest` 覆盖面更宽；端点若再改路径，只要页面发过一次即可自愈。
- **被否决的替代**：在 SW 里维护候选路径数组逐个试错（会产生多次无谓请求，且风控不友好）。

#### ADR-3：错误按成因分流，宁可不猜也不误导

- **决策**：`proxyFetch` 非 JSON 分支改为三分支——① 401/403 或**无 token** + HTML ⇒ 未登录；② **有 token** + `^<!doctype|^<html` ⇒ 「API 端点不存在（路径可能已变更）」；③ 其余 ⇒ 保留原「响应非 JSON，URL 可能不正确」。
- **理由**：本轮故障的最大成本不是功能坏了，而是**报错误导方向**（让人去重新登录）。已有 token 时拿到 SPA 文档，唯一合理解释就是路径不存在。
- **被否决的替代**：把 HTML 一律报「未登录」（即修复前逻辑，已被证明会误导）。

`extension/src/content/index.ts:432-466`：

```ts
function buildFetchPageFallback(url: string): CapturedApiRequest {
  let pathname = url;
  let search = '';
  try {
    const u = new URL(url, API_BASE);
    pathname = u.pathname;
    // 剔除游标类参数，保留其余（如 count），由 SW 翻页时重新注入游标
    const params = new URLSearchParams(u.search);
    for (const key of Array.from(params.keys())) {
      if (key.includes('cursor')) params.delete(key);
    }
    search = params.toString() ? `?${params.toString()}` : '';
  } catch {
    pathname = url.split('?')[0];
  }
  return { kind: 'fetchPage', url: `${pathname}${search}`, method: 'GET' };
}

function findRequest(kind: 'fetchPage' | 'history'): CapturedApiRequest | undefined {
  const captured = capturedRequests.find((r) => r.kind === kind);
  if (captured || kind !== 'fetchPage') {
    return captured;
  }
  const hit = recentApiUrls.find((u) => u.includes(FETCH_PAGE_MARK));
  if (hit) {
    logger.info('从捕获 URL 中发现 fetch_page 端点（请求配置未捕获，使用兜底）', hit);
    return buildFetchPageFallback(hit);
  }
  return undefined;
}
```

### 2.3 业务错误码：HTTP 200 也可能是失败

v0 API 的业务错误同样返回 `HTTP 200`，包络为 `{code, msg, data}`。修复新增 `assertBusinessOk`（`content/index.ts:399-416`），只在**同时满足** `code` 为有限非零数、`msg` 为非空字符串、对象含 `data` 字段时才判定为错误，避免误伤业务对象自带的 `code` 字段。

## 3. 增量规范（修复后契约）

> 对应传统文档：Spec / 接口契约 | 内容：代理错误分流、兜底请求构造、边界条件

### 3.1 `proxyFetch` 错误分流契约

| 条件 | 抛出的错误文本 | 语义 |
|------|----------------|------|
| `status ∈ {401,403}` | `未登录或登录已过期，请先登录…` | 真·鉴权失败，可操作 |
| `content-type` 非 JSON 且 `authToken` 非空且正文以 `<!doctype`/`<html` 开头 | `API 端点不存在（<url> 返回了页面 HTML 而非 JSON），可能是 DeepSeek 接口路径已变更…` | 路径问题，需改代码 |
| `content-type` 非 JSON 且 `authToken` 为空 | `未登录或登录已过期，请先登录…` | 真·未登录（被重定向到登录页） |
| `content-type` 非 JSON，其余情况 | `响应非 JSON（content-type: …），URL 可能不正确` | 保留原兜底 |
| JSON 解析失败 | 透传原始解析异常（并记录日志） | 空体 / 截断 |
| 响应体为 `{code≠0, msg≠空, data:*}` | `token/auth` 类 → 登录提示；其余 → `API 业务错误（code=…, msg=…）` | v0 业务错误 |
| 其余 | 正常返回 JSON | — |

### 3.2 `fetch_page` 请求构造契约

| 场景 | method | URL | 说明 |
|------|--------|-----|------|
| 捕获到页面真实请求 | 页面原样（GET） | 页面原样（含 `count`/游标） | 第一优先，绝不改写 |
| 捕获缺失但诊断列表里有该端点 | `GET` | `<path>?<保留的非游标参数>` | 剔除 `*cursor*` 参数，保留 `count` 等 |
| 完全无信息 | `GET` | `/api/v0/chat_session/fetch_page?lte_cursor.pinned=false&count=50` | 首页不带 `updated_at` |
| 第 N 页（N≥2） | 同上 | 追加 `lte_cursor.updated_at=<末条 updated_at>` 与 `lte_cursor.pinned=<末条 pinned>` | 与页面 keyset 翻页一致 |

### 3.3 边界条件矩阵

| 场景 | 预期行为 | 是否符合预期 |
|------|----------|--------------|
| 页面已捕获 `fetchPageRequest` | 原样重放，走 keyet 翻页 | ✅ 与修复前一致 |
| 捕获缺失，诊断列表含 `fetch_page` URL | content 侧发现端点 + 拼 v0 兜底，日志 `从捕获 URL 中发现 fetch_page 端点` | ✅ 自愈 |
| 捕获缺失，诊断列表也没有 | 走写死的 v0 兜底 | ✅ 仍能拉到列表 |
| 服务端改路径（如 `/v2/`） | 旧路径返回 HTML → 报「API 端点不存在」，不再报未登录 | ✅ 指向明确 |
| token 过期（`INVALID_TOKEN`，HTTP 200） | 报「未登录或登录已过期」 | ✅ 有据可依 |
| 末条会话缺 `updated_at` | 日志 warn，停止翻页，返回已拉到部分 | ✅ 不死循环 |
| 本页无新增会话 | 判定到底，`break` | ✅ 不死循环 |
| SPA 空页（`sessions: []`） | `extractSessions` 命名字段即返回空数组，判定到底 | ✅ 不误判为解析失败 |

### 4.2 任务详情与执行记录

#### 问题 1：「刷新列表」失败但导出正常

**现象**：见 §1.1。日志显示 `fetchAllSessions start` 的 URL 是 `/api/chat_session/fetch_page` 且 `method: POST`，而同一份诊断列表中其余 `/api/` 请求都带 `/v0/`。

**排查路径**：
1. 对比三功能各自依赖的 API，发现只有列表依赖 `fetch_page`（§1.1 对照表）→ 锁定范围。
2. 确认 token 正常（日志 `Auth token captured`）→ 排除真·登录失效。
3. 直连实测两条路径的 `content-type`（§2.1.3）→ 证实缺 `/v0/` 会拿到 SPA 文档。

#### 问题 2：根因——路径缺版本段 + HTML 误判为未登录

**根因**：见 §2.1.2。`/api/chat_session/fetch_page` 不存在 → `200 text/html` → 修复前的 `/<html|login/i` 判定把它归入「未登录」。

**修复**：兜底改 v0 GET（§2.2 ADR-1），错误分流（ADR-3）。

#### 问题 3：页面到底会不会发 `fetch_page`？（推翻假设 1）

**结论：会。** 逆向 `main.js` 得到 `c = rV().fetchSessions; useLayoutEffect(() => { c() }, [c])`——列表组件挂载即请求首页。`localStorage` 中仅有 `__session_page_size__`，**无会话缓存**，因此"命中缓存不发请求"不成立。

**仍未定论**：本次会话（日志窗口 16 秒）内页面确实没发该请求，只可能是 ① hook 异步注入与页面首批请求的竞态（日志显示 `07.640` 注入、`07.745` 才 `Fetch hook confirmed installed`），或 ② 侧栏列表组件未挂载。日志不足以区分。**判别方法**：看日志有无 `[content] API request captured {"kind":"fetchPage"}`。该遗留风险见 §5.4。

#### 问题 4：是不是后面改坏的？（推翻假设 2）

**结论**：分三层（§2.1.5）——① 坏兜底自 v1.0.0 就在；② v1.0.6 曾用 URL 发现绕开，v1.0.7 改为重放后该问题重新暴露，但此场景下两者等价失效，**不是主因**；③ v1.0.13 的 `02b508e` 把症状改写成「未登录」，这才是"以前没这毛病"的观感来源。

#### 问题 5：修复过程中自己引入并修掉的回归

`findRequest` 初版用正则 `/\/api\/[^/]*?chat_session\/fetch_page/i`，单测发现 `[^/]*?` **跨不过 `v0/` 的那个斜杠**，导致真实 URL 反而匹配不上（`/api/chat_session/fetch_page` 才能命中）。已改为与 hook 一致的路径后缀匹配：

```ts
const FETCH_PAGE_MARK = 'chat_session/fetch_page';
const hit = recentApiUrls.find((u) => u.includes(FETCH_PAGE_MARK));
```

> 这条记录保留在此，提醒后续同类"路径匹配"改动必须用**真实 v0 URL** 做单测，而不是凭直觉写正则。

#### 问题 6：`pages` 日志计数虚高

`logger.info('fetchAllSessions finished', { pages: page + 1 })` 在 `break` 退出时会多报 1（单次请求报 2 页）。已改为独立计数器 `attempted`（`service-worker.ts:308`），入口处 `attempted++`。

#### 问题 7：`findRequest` 端点自愈是否真被触发？（验收侧观察点）

修复上线后有三种可能且均属预期，日志可区分：

| 日志特征 | 含义 |
|----------|------|
| `API request captured {"kind":"fetchPage"...}` + `fetchAllSessions start` 的 URL 带 `/api/v0/` 且含 `lte_cursor` | 捕获成功，走「原样重放」，兜底未被触发 |
| `从捕获 URL 中发现 fetch_page 端点（请求配置未捕获，使用兜底）` | 捕获缺失，走了 ADR-2 的自愈分支 |
| 两行都没有、日志仅 `fetchAllSessions start` 带 `count=50` | 完全无信息，走了写死的 v0 兜底 |

三种路径最终都能刷出列表——这正是 ADR-1 + ADR-2 的兜底设计目的。
