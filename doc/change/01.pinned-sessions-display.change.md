## 1. 变更提案（需求背景）

> 对应传统文档：PRD / Feature Request | 职责：背景、现状、目标、影响面、验收标准

### 1.1 背景与动机

DeepSeek 页面侧栏把对话分成两组渲染：

- **置顶组**：独立折叠区块，标题取文案键 `pinnedSectionTitle`（「置顶」），折叠状态持久化在用户存储的 `pinnedSessionsFolded`；置顶数量有上限（`pinned_session_limit`，默认 99），批量置顶时用 `pinNCountChats`（「置顶 N 个对话」）提示。
- **非置顶组**：按时间线分组（今天 / 昨天 / 7 天内 / 30 天内，对应文案键 `sessionHistoryTimelineLabelToday` / `...Yesterday` / `...7days` / `...30days`）。

插件 popup 的会话管理器（v1.0.12 起）把这些会话拉成**一个扁平列表**，只渲染「序号 + 勾选框 + 标题 + 时间」，因此用户无法从插件里判断哪些对话在页面上是置顶的。

**需求**：插件列表能否区分置顶会话？

> 后续追加需求（同日，v1.0.16）：置顶会话单独成页，列表改为「置顶 / 非置顶」两个标签页；非置顶页按日期分组展示，分组可收起展开，默认只展开最近一天的分组。

### 1.2 现状结论

**能区分，数据已经就绪，唯一缺口是展示层。** 逐环节证据见 §2.1。

`pinned` 字段从接口响应一路保留到 popup 的 `SessionSummary` 中，**没有任何一层把它丢掉**，只是 `SessionItem` 与 `SessionListPanel` 从未读取过它。

v1.0.15 补齐了徽标与排序（方案 A+C）；v1.0.16 按页面侧栏的结构补齐了「置顶独立分区 + 时间线分组」（方案 B），此时插件列表的层级结构已与页面侧栏同构——差别仅在分组粒度：页面用「今天 / 昨天 / 7 天内 / 30 天内」四档粗分组，插件用**自然日**（理由见 §2.4.4）。

### 1.3 变更目标

| # | 目标 | 说明 |
|---|------|------|
| 1 | 置顶可辨识 | 置顶会话在列表中有一眼可辨的视觉标识（不依赖用户记忆顺序） |
| 2 | 顺序正确 | 置顶组在前、非置顶组在后；组内保持接口返回顺序（`updated_at` 降序） |
| 3 | 不破坏选择语义 | 序号仍连续递增；导出/删除所依赖的 `id` 集合不变（v1.0.16 起「全选」作用域收窄为当前标签页，避免置顶页误伤非置顶项） |
| 4 | 零回归 | 导出、批量删除、刷新列表（含 v1.0.14 的端点自愈与错误分流）均不受影响 |
| 5 | 不重复造数据层 | 复用已有 `pinned` 字段，不新增接口请求、不改分页游标语义 |
| 6 | 结构同构 | （v1.0.16 追加）置顶独立成页，非置顶按日期分组、可折叠，默认只展开最近一天 |

### 1.5 风险评估

- **数据可信度风险**：`pinned` 来自非官方契约（v0 内部接口），字段名或语义若变更，标记会静默失效（全部显示为未置顶）。缓解：按「缺失即视为 false」处理，不抛错、不影响列表加载。
- **顺序风险**：若对列表做重排（方案 C），会改变 `SessionItem` 的 `index`（数组下标 + 1）与「全选」判断所依赖的数组顺序。必须以 `pinned` 为唯一排序键做**稳定排序**，组内不得重排。
- **序号语义风险**：方案 B（分组）若拆成两个数组分别渲染，序号会从 1 重新计数，与「已选 X / 总数」的直观预期不一致。必须把跨组连续序号显式传下去。
- **交互风险**：`SessionItem` 整行是 `<label>`，点击任意位置都会切换勾选。徽标必须是纯展示元素（不对其绑定事件、不使用 `button`），否则会引入误勾选。
- **选择作用域风险**（v1.0.16 新增）：引入标签页后，「全选」若仍按全部会话判定，会出现「置顶页显示全选但非置顶项未选」的矛盾状态。缓解：全选判定与切换均收窄到 `currentList()`（当前标签页），工具栏同时显示「已选 X/Y（本页）· 共 N（合计）」两项计数，使批量导出/删除按钮上的总数可追溯。
- **折叠状态风险**（v1.0.16 新增）：默认只展开最近一天，其余收起。若把「折叠集合」存为渲染时的默认值，列表刷新后会丢失用户操作。缓解：只记录用户**显式点过**的分组（`Record<日期键, boolean>`），未记录的分组才套用「第一组展开」默认值；日期键稳定，刷新后仍有效。
- **无涉及风险项**：不改接口请求、不改分页游标、不改错误处理，故不会重演 v1.0.13 那种「报错误导」类问题。

## 2. 技术方案

> 对应传统文档：Design Doc | 职责：现状证据、接口契约、方案对比、落点

### 2.1 现状分析：数据链路七环核对

> 本表为 **v1.0.15 实施前的快照**，用于定位缺口；第 ⑦ 环已由 v1.0.15（徽标）/ v1.0.16（分组）补齐，当前实现见 §2.4。

| # | 环节 | 实测事实 | 结论 |
|---|------|----------|------|
| ① | 接口响应 | 逆向 `main.d1d163b7e4.js`：`json.data.biz_data.chat_sessions` 逐项映射，映射体含 `pinned: e.pinned`；同层还有 `data.biz_data.has_more` | 每条会话**自带布尔 `pinned`** |
| ② | 页面排序语义 | 游标比较 `(cur, next) => cur.pinned === next.pinned ? cur.value < next.value : !cur.pinned`，即「同组内取更小 `updated_at`；一旦进入非置顶区不再回退」 | 顺序固定为**置顶组 → 非置顶组**，组内按 `updated_at` 降序 |
| ③ | 页面首屏游标 | store 初始 `cursor = { pinned: null, value: null }`，`spread()` 产出 `{ pinned: false, updatedAt: null }`，最终请求为 `lte_cursor.pinned=false` 且**不带** `updated_at` | 见 §4.2 待确认项 1 |
| ④ | 扩展抽取 | `extractSessions` 的显式路径只有 `data.sessions` / `data.items` / `sessions`（**均不存在**），实际靠 `findArray` deep-scan 命中 `data.biz_data.chat_sessions`，且**原样返回数组元素、不做字段裁剪** | `pinned` 与 `updated_at` **完整保留** |
| ⑤ | 扩展分页 | `fetchAllSessions` 翻页时已用 `last.pinned` 注入 `lte_cursor.pinned`；去重按 `id` 且保留首次出现顺序 | 翻页语义与页面一致，顺序即接口顺序 |
| ⑥ | 类型定义 | `SessionSummary` 已含 `pinned?: boolean`（注释写明是为 keyset 游标二元组而加） | 类型层**无需改动** |
| ⑦ | 渲染 | `SessionItem` 只输出序号、勾选框、标题、日期；`SessionListPanel` 直接 `list().map()` 平铺 | **唯一缺口** |

> 因为 ⑦ 缺失而 ①⑤ 完好，实际表现是：置顶会话**大概率已经排在列表最前面**（接口顺序如此），但没有任何视觉标识，用户无法确认哪几条是置顶的——这也是「看起来没区分」的直接原因。

### 2.2 接口契约（内部 API，非官方）

```text
GET /api/v0/chat_session/fetch_page
  query: lte_cursor.pinned, lte_cursor.updated_at, count
  resp : { code, msg, data: { biz_code, biz_data: { chat_sessions: [...], has_more } } }

chat_sessions[i] = { id, title, title_type, updated_at, pinned, model_type, version, ... }
```

- `pinned`：布尔；为该会话当前是否置顶。
- `has_more`：布尔；页面用其判定「到底」，扩展目前未解析（靠「空页 / 本页无新增」判定，会多打一次请求）——见 §5.3。
- 排序：`pinned` 优先，`updated_at` 降序。
- 游标：`{pinned, updated_at}` 二元组，`lte` 模式向后翻页。

### 2.3 方案对比

| 方案 | 做法 | 改动量 | 风险 | 适用场景 |
|------|------|--------|------|----------|
| **A. 徽标标识** | `SessionItem` 渲染 `pinned` 时追加一个纯展示徽标（如「置顶」小标签），`popup.html` 补一条样式 | 约 5~8 行 | 极低：不碰顺序、序号、选择集 | 只想「看得出哪几条置顶」 |
| **B. 分组渲染** | `SessionListPanel` 拆成「置顶 / 非置顶」两个标签页，非置顶页再按日期分组 | v1.0.16 实际 +198 / -29 行（`App.tsx`）、+78 行（`popup.html`） | 中：序号必须跨组连续（用累计偏移 `g.start + i` 解决）；全选作用域需收窄到当前页 | 想让插件列表在结构上与页面一致 |
| **C. 排序兜底** | 汇总后按 `pinned` 做稳定排序（`pinned` 降序，其余保持原序） | 约 5 行 | 低：`Array.prototype.sort` 已稳定，组内不重排 | 防御自愈兜底路径或旧缓存中可能出现的乱序 |

**推荐**：**A + C**。A 解决「辨识」，C 用 5 行代码把「置顶在前」从「依赖接口顺序」变成「代码保证」，两者叠加即可覆盖全部验收项；B 作为后续可选增强，等 A 落地后按观感再定。

**实际选型演进**：

1. **v1.0.15**——按推荐先落地 A（徽标）+ C（稳定排序），最小改动验证「徽标能否正确读取 `pinned`」这个关键前提；
2. **v1.0.16**——真机确认徽标正常后，追加 B（双标签页 + 日期分组 + 折叠）。此时 C 的稳定排序已无意义（置顶项不再与非置顶项同屏），重写 `SessionListPanel` 时一并移除，非置顶列表直接使用接口返回顺序。

**被否决的替代**：
- 新增一个 `pinned=true` 的独立请求去单独拉置顶组——无必要（首页已返回）且多一次请求，风控不友好。
- 在前端按 `updated_at` 重排整张表——会打乱页面侧「置顶优先」的既定顺序，属反向操作。

**④ 分组构造：组间日期倒序 + 累计偏移**（`App.tsx:187-223`）

```ts
type DateGroup = { key: string; label: string; start: number; items: SessionSummary[] };

const dateGroups = computed<DateGroup[]>(() => {
  const groups: DateGroup[] = [];
  const index = new Map<string, DateGroup>();
  for (const s of normalList()) {
    const key = dayKeyOf(sessionTimeMs(s));    // 聚合，Map 保持首次出现顺序
    …
  }
  // 组间排序：日期倒序，日期未知的固定排最后
  groups.sort((a, b) => {
    if (a.key === UNKNOWN_DAY) return 1;
    if (b.key === UNKNOWN_DAY) return -1;
    return b.key.localeCompare(a.key);
  });
  // 排序后再分配偏移，保证编号在展开的所有分组间连续
  let offset = 0;
  for (const g of groups) {
    g.start = offset;
    offset += g.items.length;
  }
  return groups;
});
```

- 组内顺序**保持接口返回顺序**（时间倒序），不二次重排。
- `start` 在排序之后分配，因此跨分组编号连续；折叠某组后，后续组编号前移，等于「当前可见行号」。

**⑤ 折叠判定**（`App.tsx:225-241`）

```ts
/** 用户手动设置过则以其为准，否则只有第一个分组展开 */
function isGroupExpanded(key: string, index: number): boolean {
  const explicit = groupExpanded()[key];
  return explicit === undefined ? index === 0 : explicit;
}

function toggleGroup(key: string, index: number) {
  const cur = groupExpanded.peek();
  const explicit = cur[key];
  const expanded = explicit === undefined ? index === 0 : explicit;
  groupExpanded.set({ ...cur, [key]: !expanded });
}
```

**⑥ 全选收窄到当前标签页**（`App.tsx:307-325`）

```ts
function toggleAll() {
  const tab = activeTab.peek();
  const cur = sessions.peek()
    .filter((s) => (tab === 'pinned' ? Boolean(s.pinned) : !s.pinned));
  const next = new Set(selected.peek());
  const allChecked = cur.length > 0 && cur.every((s) => next.has(s.id));
  for (const s of cur) {
    if (allChecked) next.delete(s.id);
    else next.add(s.id);
  }
  selected.set(next);
}
```

> 全选仅增删当前页的 `id`，另一页的勾选保持不变；底部「导出选中 (N) / 删除选中 (N)」仍消费**跨页合计**的 `selected`。

#### 2.4.4 已定的设计取舍

| 取舍点 | 结论 | 理由 |
|--------|------|------|
| 默认标签页 | `normal`（非置顶） | 数据主体在此；无置顶会话时不会一进来就是空白页。改为默认置顶只需把 `App.tsx:40` 的 `'normal'` 换成 `'pinned'` |
| 分组粒度 | 自然日（今天 / 昨天 / MM-DD 周X / 日期未知） | 页面侧栏用「今天/昨天/7 天内/30 天内」四档粗分组，但它会让「默认只展开最近一天」失去落点；按天分才语义明确 |
| 序号 | 置顶页 1..k；非置顶页跨分组 1..m | 序号 = 当前视图行号，避开「非置顶页从 4 开始」的困惑 |
| 折叠记忆 | 只记录用户显式点过的分组 | 未记录的分组套用「第一组展开」默认值，既满足「默认只展开最近一天」，又不会在刷新后丢失用户操作 |
| 行内日期 | 保留 `YYYY-MM-DD HH:mm` | 与置顶页显示一致；组头已含日期，但统一格式减少认知成本 |
| 方案 C 的去留 | **移除** | 置顶项已不在非置顶页出现，排序成空操作，留着只会误以为顺序由代码保证 |

> 交互安全性：`SessionItem` 的根节点是 `<label>`，徽标未绑定任何事件（点击等同点整行，切换勾选）；分组头绑定的是 `click → toggleGroup`，位于 `.session-item` 之外，不会波及行内勾选。

#### 4.3.3 v1.0.17：修复分组折叠失效（实现陷阱）

1. 🐛 用户反馈：分组数据正常，但点击组头无任何反应。
2. 🔍 根因：v1.0.16 在 `dateGroups().map()` 回调体内写了 `const expanded = isGroupExpanded(g.key, gi)`，编译后为普通布尔常量，`when(el, () => expanded, ...)` 的 getter 不读任何 signal，依赖集为空；而 `each` 只订阅 `dateGroups`，点击不改变它，于是「点击 → 状态变 → 无人订阅 → DOM 不动」。详见 `doc/bugfix/02.date-group-collapse-not-reactive.bugfix.md`。
3. ✅ 修复：抽出 `DateGroupPanel` 组件，展开态改为 `computed(() => isGroupExpanded(g().key, index()))`，`when` 的 getter 读 `expanded()`，订阅链恢复。

> 教训：plain 中依赖 signal 的派生值必须在 `computed` 内或 JSX 表达式（getter）内求值；在 `map` / `each` 的回调体里赋给 `const`，等于把响应式读取搬出了追踪范围。
